design.

the system behind every color on this machine. how it is named, where each color is allowed, how one file reaches twenty programs, and the small tricks that hold it together.

the idea fits in three lines. the screen is one surface. a color is named for the job it does, never for its hue. a program asks for a job, and the theme answers with a color.

so nvim never asks for yellow. it asks for accent, and accent means one thing everywhere: you are here. switch the theme and the hue changes, but the cursor, the current line number and the prompt arrow still share it, because they share the job.

this is the same idea as css variables, applied to a whole desktop. this page uses the exact palettes the machine uses. pick one and the page repaints, along with every other page of this site you have open.

~/gits/dots main ❯ cat themes/black

2 tokens

a theme is a plain file of 39 colors. every one has a single job. click one to copy it.

surfaces · one color, then small lifts

the background never changes hue. it only gets a little lighter, a step at a time, for things that sit on top. on the generated themes each step is 1.5, 3 and 5 points of lightness. you feel the lift more than you see it.

text · four levels of attention

text is never colored to look nice. it is dimmed by how little you need it. every level is the background's own hue, so text never fights the surface.

accent · you are here

one color carries position. the lighter steps are the accent while it moves (a search as you type). the darker steps are the accent fading into the background, for apps that need softer versions of the same mark.

meaning · only when something happened

green and red are not decoration. they appear only when something was added, passed, removed or broke. blue marks places you can go: links, folders in editors, branches. the one exception is ls: its colors in LS_COLORS are older than this system, with folders green and links red.

terminal · the sixteen colors programs already know

programs that never heard of this system still speak the sixteen terminal colors. nnn, ranger and cava follow the theme only because these are set. they are tuned to the same roles: color1 is the keyword red, color2 the string green, and so on.

3 rules of use

tokens say what a color is. rules say where it may go. every rule removes something.

  1. one accent per regiona window shows the accent in one or two places at most: where the cursor is and which line it is on. if three things are accent, none of them is.
  2. lifts, not boxesa bar or a popup is separated from the surface by being one step lighter, not by a frame. the emacs mode line even draws its padding as a box in its own background color, so the box exists for spacing and is never seen.
  3. one border, one pixelwhen two things must be divided, a single line of line divides them. no double borders, no shadows, no rounded corners.
  4. color means somethinggreen and red never appear because a design wanted warmth. if you see red in an editor, a diff or a bar, something is wrong or was removed. (ls is the old exception, see meaning above.)
  5. bold almost neverbold is kept for the one heading or match you must not miss. magit's section headings are plain accent text; only the top two heading levels of a markdown note are bold.
  6. dim instead of hidecomments, line numbers and hints stay on screen at fg2 and fg3. you can always read them, you never have to.
  7. readable or refuseda generated theme whose text cannot reach 4.5:1 contrast on its background is never saved, and the test suite fails if any theme in themes/ breaks the rule.
  8. the same text everywhereone monospace face per screen: 0xProto in the terminal and emacs, JetBrains Mono on this site. no second font for headings.

4 syntax

code is colored by one mapping, shared by nvim and emacs. the same line of c looks the same in both, on every theme but gruvbox, where nvim loads gruvbox.nvim to keep the original untouched.

1 #include <stdio.h> 2 3 /* count to forty two */ 4 int main(void) 5 { 6 for (int i = 0; i < 42; i++) 7 printf("%d\n", i); 8 return 0; 9 }
color1
keywords: for, return, if. the words that change the flow.
color2
strings. text inside the program.
color3
types. what a thing is.
color4
functions, defined and called. what a thing does.
color5
constants and numbers. values that never change.
color6
the preprocessor. text that runs before the code does.
fg
variables and properties. most of the code is plain, on purpose.
fg1
operators and punctuation, one step quieter than names.
fg2
comments, in italic. present, never loud.
fg3
line numbers. the current one is the accent.

the mapping lives in two files written for two different engines: a lua table in config/nvim/colors/theme.lua and an elisp theme in config/emacs/dots-theme.el. what keeps them in step is that both read roles, never hex values. opencode's json theme follows the same idea more loosely: keywords red, strings green, numbers magenta, and functions in the accent.

~ ❯ theme black

5 how it connects

one command, one file in, twenty programs out. every program gets its colors in its own language and is told to reload in its own way.

themes/<name>39 lines of key=#rrggbb. the one place a theme's colors are written. (bash keeps fallbacks, and dwm and dmenu compile in defaults, for a machine with no theme yet.)
↓
theme <name>parses the file, refuses it if a key is missing or a value is not #rrggbb, and writes ~/.cache/theme/colors.sh for anything that wants plain shell variables.
↓ for every target in TARGETS
render_<target>writes the colors in that program's own format: a lua table for nvim, an elisp alist for emacs, a conf file for tmux, json for opencode, css for gtk, firefox and vesktop, ini for qt and obs, Xresources for st and dwm.
↓ the choice is saved to ~/.config/theme before any reload can fail
reload_<target>tells the running program, if there is one:
nvimevery server socket gets a remote command that reloads the scheme
emacsevery server socket gets (dots-theme-reload) through emacsclient
tmuxtmux source-file on the cached conf
stxrdb merges the colors, then SIGUSR1 makes st read them
dwmSIGHUP, then the bar name is set again to wake it
dunstdunstctl reload over D-Bus
gtkgsettings flips the light or dark preference
wallpaperfeh paints the flat color
the restfirefox, gimp, obs, btop and friends read the files on their next start

two more things make it hold. configs are symlinked from the repo, never copied, so editing ~/.config/nvim edits the repo and the two cannot drift. and the generated files land in the cache or in paths git ignores, so switching themes never makes the repo dirty.

6 code tricks

the parts worth stealing. every excerpt is the real code.

a theme file is parsed, never run

a theme looks like shell, so the lazy way is source themes/black. that would run anything a theme file contained. instead one sed pulls out key value pairs and ignores every other line, then each value must be exactly #rrggbb.

_theme_parse() { sed -n -E 's/^[[:space:]]*([a-z0-9_]+)=([^[:space:]#]*([#][0-9a-fA-F]*)?)[[:space:]]*(#.*)?$/\1 \2/p' "$1" }

lib/theme.sh

a whole palette from one color

theme new 2b2f2a builds all 39 colors from a single background. the math is plain awk, inside lib/generate.sh. the lifts are the background with a little more lightness, the borders a lot more, and on a light theme the sign flips so lifts get darker:

t["bg1"] = shift(bg, sg * 0.015); t["bg2"] = shift(bg, sg * 0.03); t["bg3"] = shift(bg, sg * 0.05) t["line"] = shift(bg, sg * 0.15); t["line2"] = shift(bg, sg * 0.20)

the six terminal hues sit at fixed angles on the color wheel, all at one saturation and lightness, so none of them shouts louder than another. the accent is the background's opposite hue, or a warm gold when the background has no hue at all:

split("0 95 40 210 320 175", hues, " ") ah = neutral(bg) ? 38 : B["h"] + 180

the awk as it runs, without the shell quoting around it

readable by force

fg, fg1, fg2 and every terminal color go through fix. it measures the WCAG contrast against the background and, while the ratio is under the minimum, moves lightness away from the background two points at a time. the hue stays, only the brightness gives way. fg and fg1 must reach 4.5:1, fg2 3:1, and fg3 is left dim on purpose.

function fix(c, bg, min, o, step) { hsl(c, o); step = isdark(bg) ? 0.02 : -0.02 while (cr(c, bg) < min && o["l"] >= 0 && o["l"] <= 1) { o["l"] += step; c = hslhex(o["h"], o["s"], o["l"]) } return c }

the same rules, as theme_check, run over every file in themes/ in the test suite: fg and the terminal colors need 4.5:1, color8 needs 3:1, and on a light theme each bright color must be darker than its normal one. gruvbox is marked canonical: it skips the terminal color rules so it stays true to the original, but its fg must still reach 4.5:1.

the order that never loses a choice

all files are written first, then the choice is saved, then programs are told. if a reload fails, the machine still knows the theme and the program picks it up on its next start.

for t in "${TARGETS[@]}"; do if declare -F "render_$t" >/dev/null; then "render_$t" || { warn "$t: could not write its theme files"; failed=1; } fi done # The files are written: record the theme before any reload can fail. printf '%s\n' "$THEME" > "$STATE"

only signal what can listen

st and dwm are patched to recolor on a signal. but an st built before the patch treats SIGUSR1 as a reason to quit, and you would lose your terminals. so before sending, the tool looks for the patch's own string inside the running binary.

for pid in $(pgrep -x "$name"); do if grep -qa "$marker" "/proc/$pid/exe" 2>/dev/null; then kill "-$sig" "$pid" && printf '%s\n' "$pid" else info "$name ($pid): built before the xresources patch, log out and back in to recolor it" >&2 fi done

templates with holes

css themes for gtk, firefox and vesktop are templates with {{accent}} style holes. one sed fills them. {{line_rgb}} gives 59, 62, 62 for css rgba(). if any hole is left, nothing is written, so a half themed app is impossible.

--background-modifier-hover: rgba({{line_rgb}}, 0.3);

templates/vesktop.css

no white flash in emacs

emacs paints its first frame before the theme loads, so most themes flash white for an instant. here the palette is read in early-init.el, before any frame exists, and its background goes straight into the frame settings.

(defvar dots-palette-file (expand-file-name "~/.cache/theme/emacs.el")) (defvar dots-palette nil) (load dots-palette-file t t)

the theme itself then reads the palette with let-alist, so every color is a short dotted name, close to how css reads:

(let-alist dots-palette (custom-theme-set-faces 'dots `(default ((t (:background ,.bg :foreground ,.fg)))) `(mode-line ((t (:background ,.bg1 :foreground ,.fg1 :box (:line-width 4 :color ,.bg1)))))

config/emacs

a program in two functions

adding a program means writing one file with two functions, render_ and reload_, and adding its name to the list. this is the whole of emacs:

render_emacs() { local k { printf ';;; -*- lexical-binding: t -*-\n(setq dots-palette\n (quote ((name . "%s")\n' "$THEME" for k in "${THEME_KEYS[@]}"; do printf ' (%s . "%s")\n' "$k" "${!k}"; done printf ' (add_bg . "%s")\n' "$(mix "$bg" "$green" 15)" printf ' (del_bg . "%s")\n' "$(mix "$bg" "$red" 15)" printf ' (add_bg2 . "%s")\n' "$(mix "$bg" "$green" 30)" printf ' (del_bg2 . "%s"))))\n' "$(mix "$bg" "$red" 30)" } > "$HOME/.cache/theme/emacs.el" } reload_emacs() { local sock command -v emacsclient >/dev/null || return 0 for sock in "${XDG_RUNTIME_DIR:-/run/user/$UID}"/emacs/*; do [[ -S "$sock" ]] || continue emacsclient -s "$sock" --eval '(dots-theme-reload)' >/dev/null 2>&1 || true done }

note the diff backgrounds: they are not in the theme at all. they are mixed on the fly, 15% of green into the background, so every theme gets added and removed lines that sit quietly on its own surface.

tests that cannot touch the desktop

a theme test that reached the live tmux or dwm would repaint the machine while it ran. every test gets its own home, its own runtime folder for sockets, no X display and no D-Bus, so every reload finds nothing to talk to.

FAKE_HOME="$(mktemp -d)" export HOME="$FAKE_HOME" export TMUX_TMPDIR="$FAKE_SESSION/tmux" export XDG_RUNTIME_DIR="$FAKE_SESSION/run" unset DBUS_SESSION_BUS_ADDRESS TMUX unset DISPLAY

7 make your own

three ways in, from easiest to deepest.

from one color

❯ theme new 2b2f2a a whole theme, named after the color ❯ theme new 2b2f2a moss same, with your own name

if the color cannot make readable text, nothing is saved and the tool says why.

by hand

copy a file in themes/, change its values, run theme <name>. a missing key or a malformed value stops it and names the key. run bats tests/theme.bats to hold it to the contrast rules too.

a new program

  1. write lib/targets/<name>.sha render_<name> that writes the colors where the program reads them, and a reload_<name> that tells a running one, or does nothing.
  2. add it to TARGETSone word in the theme script.
  3. map roles, not colorsask what each part of the program is for, then pick the token with that job. if nothing fits, the program is probably showing something it does not need.
  4. test it in a fake homecopy one of the target tests in tests/: apply a theme, read the color the program ended up with, compare it to the theme file.

the reasons behind each program's setup, not only its colors, are in the blog.
