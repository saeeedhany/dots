one machine, many programs.

23 oct 2026 · 8 min

most setups are a pile of programs that each look good alone. this one tries to be one program with many windows. this post walks through how nvim, emacs, tmux and bash are set up, and the few ideas that make them feel like the same thing.

1 roles, not colors

the first idea is borrowed from the web. a stylesheet that says color: #c2a46a in forty places is a stylesheet you will never change. one that says color: var(--accent) changes in one line. the value is chosen once; everything else asks for the name.

the same trick works for a whole desktop if every program agrees on the names. here the names are jobs: bg is the surface, fg2 is text you can skip, accent is where you are. a program is never told "yellow". it is told what the thing on screen is for, and the theme decides the color.

the shell is the smallest example. bash reads the current theme from a plain file, with a fallback for every color so a fresh machine still has a prompt:

_theme_hex() { printf '%s' "${_theme[$1]:-$2}"; }

PS1="...\w...\$(_git_branch) \[\e[38;2;$(_theme_rgb accent '#c8a46b')m\]❯\[\e[0m\] "

home/bashrc, the prompt trimmed to its colors

the prompt asks for accent, never for gold. when the theme changes, the arrow changes with the cursor in nvim and emacs and the session name in tmux, because they all asked for the same job.

the theory behind this has a name in design systems: design tokens. the point is not reuse. the point is that a name carries intent, and intent survives a change of value. if the arrow were simply gold, nobody would know it is supposed to match the cursor.

2 nvim: what it shows, what it hides, why

nvim is the daily editor, so it is the most configured program here. it carries a real plugin set: telescope to find files, completion, tree sitter, language servers, git signs, surround. but the settings around those plugins are mostly about two things: keeping the text still, and removing what is not used.

it keeps the text still

vim.opt.signcolumn = "yes"
vim.opt.colorcolumn = "80"
vim.opt.cursorline = true
vim.opt.scrolloff = 8

config/nvim/lua/core/options.lua

the sign column is always on, even when there is nothing to show. without it, the first git change or diagnostic pushes every line two columns to the right, and your eye has to find its place again. a column that never moves is a small thing you stop noticing, which is the goal. the same goes for scrolloff: the cursor never touches the edge, so you always see where you are going.

it dims instead of hiding

the numbers are both absolute and relative, so 12j is readable at a glance, but they sit at fg3, the dimmest text level. only the current line number gets the accent. you can always read them; you never have to. (on the gruvbox theme nvim loads gruvbox.nvim instead, so the original stays untouched; everything in this section about colors is the scheme every other theme uses.)

it hides what nobody uses

local disabled_built_ins = {
  "2html_plugin",
  "getscript",
  "gzip",
  "tar",
  "zip",
  "tutor",
  ...
}

config/nvim/lua/core/options.lua, trimmed

vim ships with plugins for reading zip files and converting buffers to html. they load on every start. turning them off is free speed and one less thing to surprise you. the netrw banner goes too.

it keeps the keys stock

map({ 'i', 'v', 's' }, 'kj', '<Esc>', { desc = 'Exit to Normal mode' })
map('t', 'kj', [[<C-\><C-n>]], { desc = 'Exit terminal mode' })
map('n', '<C-p>', '<cmd>Telescope find_files<cr>', { desc = 'Find files' })

config/nvim/lua/core/keymaps.lua, all of it

that is the whole keymap file. everything else is what nvim already does: K for docs, grn to rename, gra for code actions, grr for references, all built into nvim 0.11, and CTRL-] jumps to a definition through the language server. the reason is simple. a stock key is documented in :help, works on every machine you sit at, and is what every answer online assumes. a custom key is a private language you have to keep translating.

it fixes friction where it happens

a few autocommands do the boring work: trailing whitespace is removed on save, missing folders are created when you save into them, and the cursor goes back to where you left it when you reopen a file. each one exists because something annoyed the same way twice.

it does not paint the background

Normal = { fg = c.fg },
NormalFloat = { fg = c.fg, bg = c.bg1 },
CursorLineNr = { fg = c.accent, bold = true },

config/nvim/colors/theme.lua

Normal has no background at all, so the terminal's shows through. nvim is not a window on the surface; it is part of the surface. floating windows get bg1, one lift up, which is how you know they are on top.

3 emacs: built in first, packages only from friction

emacs is the opposite case. it is new here, it is being learned, and it is kept close to what ships. emacs 31 already has a vertical completion menu, a key hint popup, a language server client, tree sitter modes and a markdown mode. so the config mostly turns those on.

(fido-vertical-mode 1)
(global-completion-preview-mode 1)
(which-key-mode 1)

config/emacs/init.el

why built in first

every package you add is a small debt. it has its own keys to learn, its own updates that can break, and its own way of doing what emacs already does. when you are learning an editor, a package also hides the editor from you: you learn the package instead. built in tools are documented in the manual you already have, under C-h.

packages come in only when something real hurts, and each one is the best answer to one need: magit for git, denote for notes, auctex for latex, vterm for a real terminal. if you cannot name the friction a package fixes, it does not go in.

let it do the boring setup

(setq treesit-auto-install-grammar 'always)
(setopt treesit-enabled-modes t)

older setups carried a list of grammar urls and a command to install them. emacs 31 knows where its grammars live and can fetch one the first time you open a file that needs it. two lines replace a page. note setopt on the second line: that option runs code when it is set, which a plain setq skips.

keep the machine out of the repo

(setq user-emacs-directory (expand-file-name "~/.local/share/emacs/")
      package-user-dir (expand-file-name "elpa" user-emacs-directory)
      custom-file (expand-file-name "custom.el" user-emacs-directory))

config/emacs/early-init.el

the config folder is a link into the repo. emacs, left alone, writes history, caches and installed packages into that same folder. the first line moves all of that to ~/.local/share/emacs, so the folder holds only what a person wrote. the same rule is why generated theme files land in ~/.cache or in paths git ignores.

4 tmux and bash: the bar and the one line prompt

the tmux bar is part of the floor

set -g status-style "bg=$bg,fg=$fg1"
set -g window-status-format " #[fg=$fg2]#I:#W "
set -g window-status-current-format " #[fg=$fg,bold]#I:#W#[nobold] "

lib/targets/tmux.sh, the generated part

the bar has the surface color, not a colored strip. windows you are not in are fg2; the one you are in is fg. there is no box and no colored powerline blocks. the session name on the left is the one accent, because it is where you are, and nothing else on the bar needs to look more important than the text you are working on.

splits open in the folder you are already in, panes move with h j k l, and sessions are saved every fifteen minutes and restored when tmux starts. a session should outlive the terminal, a reboot, and you.

one line, same column

~/gits/dots main ❯ theme black

the prompt is one line: the folder, the branch dimmed, and an arrow. no user, no host, no clock. those answer questions you are not asking while typing a command. keeping it on one line also means the arrow and the command move only as far as the path is long, and nothing above it jumps around when the branch changes.

the arrow is the only accent on the line, for the same reason the current line number is: it is where you are. bash also runs in vi mode (set editing-mode vi in inputrc), so the motions from nvim work on the command line, and z jumps to recent folders in plain bash, without installing anything.

5 what they all agree on

once the programs share colors, it becomes easy to notice where they disagree on anything else, and to fix it. a few agreements came out of that.

  1. the same keys mean the same thingh j k l move between panes in tmux, between lines in nvim and bash, and j k between windows in dwm. b hides the bar in dwm (super b), in tmux (prefix b), and on this site.
  2. quietno bells anywhere: tmux has visual and audible bells off, emacs rings nothing, and notifications come from one place, dunst, in the same flat color.
  3. stillcolumns that never jump, prompts that never wrap, bars that never resize. movement is reserved for things that actually changed.
  4. flatlifts instead of boxes, one 1px line where a border is needed, and bold only where you must not miss something.
  5. linked, not copiedevery config is a link into one repo. editing a setting on the machine is editing the repo.

none of these is clever. the value is in having all of them at once, because then nothing on the screen surprises you, and the screen stops asking for attention.

6 how to take the idea into your own setup

you do not need this repo for any of it. the idea works with whatever you already run.

  1. name your jobs firstbefore picking a single color, write down what things on your screen are for: the surface, a lifted surface, a border, text at three or four levels of importance, "you are here", added, removed. that list is your theme's shape.
  2. write one fileput the values in one plain file. everything else should read from it, never contain a hex value of its own.
  3. teach each program to read ita small script per program that writes the file it understands: a lua table, an elisp list, a conf file. this is the only place a program's quirks live.
  4. reload, don't restartmost programs can be told to reread their colors: a socket, a signal, a command. finding that hook is what makes a switch feel instant.
  5. start from the defaultsfor keys and behavior, change something only after it bothered you twice. keep the reason next to the change, even if only in your head.

the full system, with every token and the code behind it, is on the design page. the configs themselves are in the repo.
